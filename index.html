Level 01
Issue Hierarchy

Understand how work is structured in Jira — from big initiatives down to individual tasks.

🟣
Level 1 — Epic
Epic
A large body of work spanning multiple sprints. Think of it as a feature or initiative — broken down into Stories.
📌 Examples: "User Auth Flow", "Checkout Redesign", "Mobile Onboarding"
⏱ 2–6 sprints👤 Product Manager
🟢
Level 2 — Story
User Story
A piece of user-facing value written from the user's perspective. Must fit within a single sprint.
📌 "As a [user], I want [goal] so that [benefit]"
⏱ 1 sprint👤 PM + Dev Lead
🔵
Level 3 — Task
Task
Technical or operational work that doesn't directly deliver user value but is required. Can exist independently of a story.
📌 "Set up CI/CD pipeline", "Write API docs", "DB migration"
⏱ Hours–days👤 Developer
🟡
Level 4 — Sub-task
Sub-task
Smaller atomic units under a Story or Task. Useful for breaking complex work into trackable pieces for different people.
📌 "Design Figma mocks", "Write unit tests", "QA testing"
⏱ Hours👤 Individual contributor

Level 02
Creating Issues

Step-by-step instructions for creating each issue type correctly in Jira.

🟣 Epic
🟢 Story
🔵 Task

🟣
How to Create
Epic
1
Open your Jira project
Go to the Backlog or Roadmap view of your project.
2
Click "+ Create" → Select "Epic"
Issue type dropdown is in the create modal at the top.
3
Fill in Epic Name
Short, descriptive label used across the board (e.g., "User Auth", "Checkout v2")
4
Write the Summary & Description
Explain the business goal, target users, and high-level scope. Link to the PRD.
5
Set Start & Due Date, Priority, Assignee
Assign to the PM who owns this feature area.
⚠️ Don't use Epics for work that fits in a single sprint. If it's small, make it a Story instead.
🟢
How to Create
User Story
1
Click "+ Create" → Select "Story"
Or open the Epic and click "Create child issue" to auto-link it.
2
Write the Summary in user story format
"As a [persona], I want [capability] so that [benefit]"
3
Link it to the parent Epic
Use the "Epic Link" field to connect this story to its Epic.
4
Add the full description
Include context, Figma link, API contract reference, and acceptance criteria.
5
Set Story Points & add to Sprint
Estimate complexity, assign sprint, set priority and assignee.
✅ A good story is small enough to complete in one sprint and clear enough that any developer can understand it.
🔵
How to Create
Task
1
Click "+ Create" → Select "Task"
Tasks are usually created by developers or tech leads for technical work.
2
Write a clear action-oriented Summary
Start with a verb: "Set up", "Create", "Migrate", "Configure", "Write"
3
Link to parent Story (optional)
If it supports a story, link it. Otherwise it can be standalone.
4
Add story points & assign to developer
Estimate the effort and assign to the engineer who will own it.
⚠️ Tasks are for technical work. If something delivers user value — make it a Story instead.
🟡
How to Create
Sub-task
1
Open the parent Story or Task
Navigate to the issue you want to break down further.
2
Click "Create Sub-task" in child issues section
Sub-tasks are always created from inside a parent issue.
3
Write a specific, atomic summary
One sub-task = one clear deliverable. "Design Figma screens for login page"
4
Assign to the right person
Design → Designer · Test → QA · Code → Developer
✅ Common sub-tasks: Design Mocks, FE Implementation, BE API, Unit Tests, QA Testing, Code Review, Documentation
Level 03
Story Description Template

Use this template for every User Story. Consistent descriptions = faster development and fewer back-and-forths.

📋 Full Story Template
## 🎯 User Story
As a [type of user / persona],
I want to [perform some action / achieve some goal],
So that [benefit / value / outcome].

## 📄 Context & Background
[Why are we building this? What problem does it solve? Business value? Link to PRD.]

## ✅ Acceptance Criteria
Given [precondition], When [action], Then [outcome].
Given [another scenario], When [action], Then [outcome].

## 🎨 Design Reference (Figma)
🔗 Figma Link: [Paste Figma frame URL here — link to specific frame, not whole file]
📐 Screens: [Login Screen, Error State, Empty State, Mobile View]
🖱️ Prototype: [Link to interactive Figma prototype]

## 🔌 API Contract
📬 Endpoint(s): [GET /api/v1/users or POST /api/v1/orders]
📄 API Docs: [Link to Swagger / Postman / Confluence]
📦 Request Payload: [Brief description or link to schema]
📤 Response: [Brief description of response structure]
⚠️ Error Cases: [401 Unauthorized, 404 Not Found, 500 Server Error]

## 🚫 Out of Scope
[Explicitly list what is NOT included to avoid scope creep]

## 🔗 Dependencies
[Other stories, teams, or systems this story depends on]

## 🧪 Testing Notes
[Edge cases, devices to test, test accounts, feature flags]
✅ Good Story Example
Summary: As a returning user, I want to log in with Google so that I don't have to remember a password.

AC 1: Given I'm on the login page, when I click "Continue with Google", then I'm redirected to Google OAuth.
AC 2: Given OAuth succeeds, then I'm logged in and redirected to my dashboard.
AC 3: Given OAuth fails, then I see "Login failed. Try again."
❌ Bad Story Example
Summary: Google login

Description: Add Google login to the app.

What's wrong:
• No user persona stated
• No benefit or value given
• No acceptance criteria
• No Figma link
• No API details — too vague to build

🃏 Planning Poker Process
1
PM reads the story aloud
Team asks clarifying questions freely.
2
Each person picks a number silently
No influencing others before the vote.
3
Reveal simultaneously
Discuss the highest and lowest votes.
4
Reach consensus & log in Jira
Re-vote if needed. Record the agreed number.
💡 What to Consider
  • ◈How complex is the logic?
  • ◈How many systems/services are involved?
  • ◈How much uncertainty or unknowns exist?
  • ◈Does it require design work?
  • ◈Does it touch legacy code?
  • ◈How much testing is needed?
  • ◈Are there dependencies on other teams?
  • ◈Has anyone done this type of work before?
Level 05
Capacity Planning

Plan how much work your team can realistically complete in a sprint, accounting for leaves and overhead.

Team Capacity (pts) = Σ Available Days per Person
Since 1 SP = 1 Day = 6 Hours, every available day = 1 story point
✅ Commit to 70–80% of capacity to account for unexpected work, meetings, and spillover.

Level 06
Figma & API Contracts

How to properly reference designs and API specs so your team has everything to build.

🎨 How to Add Figma Links

In Figma, always link to the specific frame — not the entire file. Right-click any frame to copy its direct link.

1
Open Figma → select the specific frame
Click on "Login Screen v3" — not the whole page.
2
Right-click → "Copy link to selection"
Or use the Share button → copy link.
3
Paste in the Jira story description
Under the "🎨 Design Reference" section of your story template.
Include these in the Figma section:
  • ◈Happy path / main screen
  • ◈Error states
  • ◈Empty states
  • ◈Responsive / mobile views
  • ◈Interactive prototype link
  • ◈Design version (v1, v2, Final)
  • ◈WIP status note if not finalized
⚠️ Never start development with a WIP design. Confirm "Design Ready" with designer first.
🔌 How to Document API Contracts

The API contract defines how frontend and backend communicate. PMs should work with the BE lead to have this ready before sprint starts.

## API Contract — Login with Google Endpoint: POST /api/v1/auth/google Auth: None (public endpoint) --- Request Body --- { "id_token": "<Google OAuth token string>", "device_id": "string (optional)" } --- Success Response (200) --- { "access_token": "eyJhbGciOiJIUzI1NiIsInR...", "user": { "id": "usr_123", "email": "user@example.com", "name": "Jane Doe" } } --- Error Responses --- 401 → Invalid or expired Google token 403 → Account suspended 500 → Internal server error --- Swagger / Postman --- Docs: https://api-docs.company.com/auth
✅ A good API contract includes:
  • ◈HTTP method + endpoint path
  • ◈Authentication requirements
  • ◈Request body / query params
  • ◈Success response structure
  • ◈All possible error codes & meaning
  • ◈Link to Swagger / Postman docs
