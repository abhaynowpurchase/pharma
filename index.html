Process Evolution

What changed and why

❌ Old Process Problems

  • Mid-sprint design changes allowed
  • Requirements changed after freezing
  • Feedback could come at any time
  • Developers restarted work from scratch
  • No clear gate for ticket readiness
  • "Not up to mark" subjective rejections
  • Unpredictable sprint commitments

✅ New Process Strengths

  • Design frozen before sprint starts
  • All stakeholders review tickets upfront
  • Impact analysis documents scope clearly
  • Reviews only for deviations from plan
  • Changes via formal change requests
  • Production bugs take clear priority
  • Predictable, sustainable delivery

🎯 Core Improvement

The new process eliminates rework by ensuring all stakeholders align on requirements, design, and approach before development begins. This protects developer time and ensures realistic sprint planning.

Ticket Readiness Gate

The critical checkpoint before sprint entry

🚫 HARD RULE: No Incomplete Tickets in Sprint

If anything is missing in the ticket, it cannot be taken into the sprint. Period.

✅ Ticket Must Have

  • ✓ Complete FRD documented
  • ✓ Final design approved by design team
  • ✓ All acceptance criteria clear
  • ✓ Senior engineering manager & tech lead review completed
  • ✓ Product owner sign-off
  • ✓ All stakeholder approvals

👥 Who Reviews Tickets

  • Senior Engineering Manager & Tech Leads: Technical feasibility & approach
  • Product Owner: Requirements & business value
  • Design Team: UI/UX completeness
  • QA Lead: Testability & acceptance criteria
  • Other Stakeholders: Dependencies & integration

💡 Shared Responsibility

Both leads and all stakeholders are responsible for ticket correctness. Everyone must review and approve. Only properly vetted tickets can enter the sprint.

Impact Analysis Document

Developer's blueprint for implementation

📊 What is Impact Analysis?

A document uploaded by the developer to the Jira ticket that outlines exactly what they plan to do, which files will be changed, what the technical approach will be, and what the impact is on the system.

Document Should Include

  • • Technical approach & architecture
  • • Files/modules to be modified
  • • Database changes (if any)
  • • API endpoints affected
  • • Dependencies on other systems
  • • Estimated effort breakdown
  • • Potential risks & mitigation

Review Process

  • 1. Developer uploads impact analysis to ticket
  • 2. Tech lead/senior engineering manager reviews the approach
  • 3. Lead approves or requests changes
  • 4. Once approved, dev starts implementation
  • 5. Implementation must follow the approved plan

✅ Protection for Developers

The impact analysis creates a clear contract. Reviews can only happen if the developer deviated from the approved design or went beyond the impact analysis scope. If the developer followed the plan, the ticket is complete.

Design Freeze Rule

No mid-sprint design changes

🚫 ABSOLUTE RULE

Once a sprint starts, design is FROZEN. No changes allowed.

❌ NOT Allowed Mid-Sprint

  • ✗ "Let's change the button color"
  • ✗ "Add this field to the form"
  • ✗ "Let's move this section"
  • ✗ "Can we use a different layout?"
  • ✗ "I just thought of a better flow"

✅ What Happens Instead

  • ✓ Design was reviewed before sprint
  • ✓ Designer signed off on design
  • ✓ Everyone adheres to approved design
  • ✓ Developer follows design exactly
  • ✓ New ideas → Change Request or next sprint

📝 The Contract

Design team reviewed their design before sprint start.

All stakeholders approved the design.

Therefore, everyone must adhere to it. No exceptions.

⚠️ Exception: If there's a genuine usability issue or technical impossibility discovered during development, it must go through the formal Change Request process.

Review Rules

When reviews can and cannot happen

✅ Reviews ARE Allowed For:

  • ✓ Design deviation: Developer didn't follow approved design
  • ✓ Scope creep: Work beyond impact analysis
  • ✓ Code quality issues: Standards not met
  • ✓ Technical errors: Bugs, performance issues
  • ✓ Security concerns: Vulnerabilities found

❌ Reviews NOT Allowed For:

  • ✗ "Not up to mark" without specifics
  • ✗ New requirements discovered mid-sprint
  • ✗ Design changes after freeze
  • ✗ Personal preferences on approved design
  • ✗ Subjective opinions on completed work

🎯 The Standard

If the developer followed the approved design and stayed within the impact analysis scope, the ticket is complete. Reviews should only address deviations, technical issues, or quality concerns — not subjective preferences or new ideas.

💡 Senior Engineering Manager & Tech Lead Responsibility

Senior engineering manager & tech leads review impact analysis at the start. After approval, only deviations or technical problems warrant further review. This protects developer time and maintains sprint predictability.

Change Request Process

How to handle mid-sprint requirement changes

⚠️ When Requirements Change Mid-Sprint

If requirements that were frozen change during the sprint, this must be handled through a formal Change Request — it cannot just be added to the existing ticket.

Change Request Workflow

⚠️ Requirement Change Identified
↓
📝 Change Request Created
(Separate ticket/document)
↓
📊 Impact Assessment
(Senior engineering manager & tech lead evaluate scope, time, risk)
↓
👥 Stakeholder Review
(Product, Senior Engineering Manager & Tech Lead, relevant parties)
↓
🔍 Decision Point

✅ Approved

Goes to next sprint planning

❌ Rejected

Change documented for future consideration

🔑 Key Points

• Original ticket continues with original requirements

• Change request is a separate entity

• Current sprint commitment is protected

• Changes are planned properly for future sprints

Production Bug Handling

Priority interrupt for critical issues

🚨 Production Bugs Take Priority

When a production bug occurs, it gets immediate attention and can interrupt current sprint work.

Bug Handling Process

🐛 Production Bug Identified
↓
🔴 Priority Assessment
(P0/P1/P2/P3)
↓
⏸️ Pause Non-Priority Ticket
(Drop the ticket that's not at priority)
↓
🔧 Developer Assigned to Bug
↓
🛠️ Bug Resolution
(Fix, test, deploy)
↓
✅ Bug Resolved & Deployed
↓
📋 Return to Paused Ticket
(Can be taken in next sprint if needed)

When to Drop Current Work

  • P0 (Critical): Always interrupt immediately
  • P1 (High): Interrupt if affecting users
  • P2 (Medium): Evaluate with senior engineering manager & tech lead
  • P3 (Low): Queue for next available slot

Paused Ticket Handling

  • • Document current progress
  • • Commit work in progress
  • • Mark as "paused for prod bug"
  • • Can resume in next sprint
  • • No penalty for sprint miss

✅ Developer Protection

If a ticket was dropped for a production bug, this is documented and understood. The developer can pick up the paused ticket in the next sprint with no negative impact on their performance metrics.

Bug Reporting Process

How bugs are reported and validated

Bug Lifecycle

🐛 Bug Discovered
↓
📝 Product Team Reports in Jira
(Complete description, steps to reproduce, expected vs actual behavior)
↓
👨‍💻 Developer Assigned for Analysis
↓
🔍 Developer Investigation
(Reproduce, analyze root cause, verify if it's actually a bug)
↓
⚖️ DECISION POINT

✅ Confirmed Bug

  • • Developer adds findings/comments
  • • Marks as "Confirmed Bug"
  • • Priority assigned (P0/P1/P2/P3)
  • • Ticket enters sprint cycle as per priority

❌ Not a Bug

  • • Developer explains why it's not a bug
  • • Could be: feature request, expected behavior, user error, env issue
  • • Marks as "Not a Bug"
  • • Ticket closed or converted to feature request

🔑 Critical Rules

• Product team reports bugs in Jira with complete details

• Developer must analyze and comment findings before any action

• Only after developer comments can the ticket move to sprint cycle

• Priority determines when the bug enters sprint (P0 immediate, P3 can wait)

📋 Required in Bug Report

  • • Clear description of the issue
  • • Steps to reproduce
  • • Expected behavior
  • • Actual behavior
  • • Environment details
  • • Screenshots/videos if applicable

🔍 Developer Analysis Should Include

  • • Reproduction confirmation
  • • Root cause analysis
  • • Bug/Not a bug determination
  • • Explanation of findings
  • • Estimated effort (if bug)
  • • Impact assessment (if bug)

Priority Ticket Management

Handling urgent tickets during an active sprint

⚡ When High Priority Tickets Arrive Mid-Sprint

Sometimes critical priority tickets need to be taken up in the current sprint. When this happens, sprint capacity must be managed by moving lower-priority tickets to the next sprint.

Priority Ticket Insertion Process

🚨 High Priority Ticket Identified
(P0 or P1 that can't wait for next sprint)
↓
📊 Assess Current Sprint Capacity
(Senior engineering manager & tech lead + team evaluate available bandwidth)
↓
🎯 Identify Ticket(s) to Move Out
(Select lower priority tickets from current sprint)
↓
🤝 Stakeholder Communication
(Inform product owner & affected parties)
↓
📋 Move Lower Priority Ticket(s) to Next Sprint
(Update Jira, adjust sprint planning)
↓
✅ Add Priority Ticket to Current Sprint
(Begin work immediately)

📝 Selection Criteria for Moving Tickets

  • 1 Lowest business priority in current sprint
  • 2 Least dependencies on other tickets
  • 3 Tickets not yet started or in early stages
  • 4 Similar effort estimate to incoming priority ticket
  • 5 No hard deadlines in current sprint

✅ Required Steps

  • ✓ Senior engineering manager & tech lead approve the swap
  • ✓ Product owner is informed
  • ✓ Sprint board updated in Jira
  • ✓ Team notified in standup/Slack
  • ✓ Moved ticket added to next sprint backlog
  • ✓ Documented in sprint notes

💡 Key Principles

• Sprint capacity should remain constant - if something comes in, something must go out

• Never overload the team - maintain sustainable pace

• Clear communication with all stakeholders is mandatory

• Moved tickets are guaranteed a spot in next sprint planning

❌ Don't Do This

  • ✗ Add priority ticket without removing others
  • ✗ Remove tickets without stakeholder notification
  • ✗ Expect team to "just work harder"
  • ✗ Pull out tickets that are 80%+ complete

✅ Do This Instead

  • ✓ Maintain constant sprint capacity
  • ✓ Communicate proactively with all parties
  • ✓ Document the swap decision and rationale
  • ✓ Protect nearly-complete work from removal

Communication Channels

Right channel for right urgency

P0 Critical

Phone Call

+ War Room

+ Incident Channel

No async allowed

P1 High

Direct Message

+ @mention in Slack

+ Email to leads

Response < 1 hour

P2 Medium

Team Channel

+ Ticket Assignment

+ Daily Standup

Response < 4 hours

P3 Low

Ticket System

+ Sprint Planning

+ Backlog Review

Response < 1 day

📢 Regular Ceremonies

  • Daily Standup (DSM): 15 min, progress, blockers & bug triage
  • Sprint Planning: Wednesday, 1 hour
  • Sprint Retrospective: Tuesday, 45 min
  • Grooming Session: Monday, 1 hour

⚡ When to Escalate

  • Blocked for more than 4 hours (P0/P1) or 1 day (P2)
  • Need architectural decision or major design change
  • Requires additional resources or budget
  • Impacts other teams or external dependencies
  • Sprint commitment at risk
  • Scope creep or requirement changes mid-sprint

⚠️ Escalate early, not late. Don't wait until the problem becomes critical.
