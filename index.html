1. Good Quality Code

Non-Negotiable Standards

⚠️ Code will NOT ship if quality gates fail

Frontend Standards

  • ESLint strict mode enabled
  • No 'any' types allowed
  • No unused variables
  • No console statements
  • React hooks exhaustive deps
  • No direct DOM manipulation
  • Stylelint with design tokens only

Backend Standards

  • ESLint or language equivalent
  • Cyclomatic complexity threshold
  • Mandatory input validation
  • Error handling required
  • Security best practices
  • API documentation complete

👉 CI must fail if lint fails — No manual override allowed

PR Quality Rules

❌ A PR is INVALID if:

  • No tests added or updated
  • No error handling implemented
  • No loading / empty / failure states (Frontend)
  • Logic duplicated across codebase
  • Naming unclear or ambiguous
  • Business logic inside UI components
  • "Works on my machine" ≠ acceptable

✅ Before Merge

  • All linting checks pass
  • All tests pass
  • Code reviewer approval
  • No unresolved comments
  • Documentation updated

✅ Best Practices

  • Raise PRs early (not last day)
  • Keep PRs focused and small
  • Add clear descriptions
  • Include screenshots (UI changes)
  • Self-review before requesting

2. Sprint & Delivery Process

2-Week Sprint Cycle

Sprint Start: Wednesday • Sprint End: Tuesday

Week 1
Build + Initial QA

  • Sprint kickoff on Wednesday
  • Scope frozen for sprint
  • Development & implementation
  • Parallel QA testing
  • Write automation tests
  • Quick feedback loops
  • Bug fixes same sprint

Week 2
Stability + Grooming

  • Monday & Tuesday:
  • ❌ NO new feature development
  • 🐞 Production bugs only
  • 📋 Impact analysis
  • 🧹 Ticket grooming
  • Sprint retrospective
  • Next sprint planning

This buffer exists because production bugs WILL come

Week 1: Build + Initial QA

Wednesday → Tuesday

👨‍💻 Dev Team Responsibilities

  • Implement assigned features
  • Raise PRs early in the week
  • Ensure lint + tests pass
  • Get reviewer approval
  • Write automation tests
  • Fix QA feedback quickly
  • Update documentation

🎯 Product Team Responsibilities

  • Test features as delivered
  • Log issues immediately
  • Validate acceptance criteria
  • Provide clear feedback
  • Real-time communication
  • Edge case testing

⚡ Parallel Workflows

Dev and QA run in parallel from Wednesday through Friday. This means features are tested as soon as they're delivered, creating faster feedback loops and allowing bugs to be fixed within the same sprint.

Week 2: Monday & Tuesday

⚠️ CRITICAL RULE

NO New Feature Development

What IS Allowed:

🐞 Production Bugs (P0/P1)

Critical issues affecting users in production require immediate attention and context switch

📋 Impact Analysis

Analyze complexity and dependencies for upcoming sprint work

🧹 Ticket Grooming

Refine backlog, clarify requirements, prepare tickets for next sprint

📋 Product Team Must Provide

  • Final Figma designs
  • Complete PRD with scope
  • Edge cases documented
  • Acceptance criteria defined
  • API contracts specified
  • Dependencies mapped

💻 Dev Team Must Provide

  • Impact analysis
  • Effort estimation
  • Risk identification
  • Technical constraints
  • Flag unclear requirements
  • Propose alternatives

Only "Ready" tickets with complete requirements enter the sprint

Backlog Rule

✅ Allowed

Product team may continue adding tickets to the backlog at any time for future sprints. This ensures continuous planning and preparation for upcoming work.

❌ Not Allowed

Product team cannot inject new features into the active sprint once it has started, unless it's a critical production bug (P0/P1).

Why This Matters

Scope stability is critical for predictable delivery. Mid-sprint changes disrupt planning, affect velocity accuracy, and create stress for the team. The sprint boundary provides a clear commitment point that both product and engineering can rely on.

4. Production Bug Handling

Severity-Based Response

P0 / P1 Bugs

Immediate context switch

Drop everything and fix. These bugs affect core functionality, cause data loss, security vulnerabilities, or prevent users from completing critical workflows.

P2+ Bugs

Planned into next sprint

Non-urgent issues that don't block critical functionality. These are groomed, estimated, and scheduled for the next sprint alongside regular feature work.

Dev bandwidth on Monday-Tuesday (Week 2) exists specifically for handling production bugs

Bug Severity Definitions

  • P0: System down, data loss, security breach
  • P1: Core feature broken, blocks critical workflows
  • P2: Minor feature issue, workaround available
  • P3: Cosmetic issue, no functional impact

5. Ownership & Escalation Matrix

Clear Roles and Responsibilities

Senior Engineering Manager

Role: Escalations only, remove blockers, assist leads when stuck
NOT: Micromanagement, day-to-day delivery tracking
Escalation: Senior EM → CTO
Scope: Entire dev organization

Frontend Architect / Tech Lead

Responsible for: Frontend delivery, sprint execution, code quality
Activities: Review all FE PRs, mentor team, unblock developers
Escalation: FE Team → FE Architect → Senior EM

Backend Delivery Lead

Responsible for: Backend sprint delivery, team coordination
Activities: Cross-team dependencies, timeline tracking
Escalation: BE Team → BE Delivery Lead → Senior EM

Backend Review Lead

Critical Separation: Code quality ONLY, no delivery pressure
Authority: Can block release if code quality is poor
Principle: "Bad code does not ship" is absolute

Developer Responsibilities

Frontend & Backend Developers

Core Responsibilities

1

Deliver assigned stories within sprint

Complete all committed work by sprint end, maintaining quality standards

2

Write comprehensive tests

Unit, integration, and E2E tests for all new features and bug fixes

3

Raise risks early

Flag blockers, unclear requirements, or scope concerns immediately

4

Follow coding standards

Adhere to linting rules, naming conventions, and architectural patterns

Escalation Path: Developer → Line Manager / Lead → Architect / Delivery Lead

6. Why This Works

Key Design Decisions

🎯

Clear Ownership

Every role has defined responsibilities with no overlap or ambiguity

⚖️

Quality vs Delivery Separated

Review lead focuses solely on quality without delivery pressure

🛡️

Buffer for Reality

Monday-Tuesday buffer handles inevitable production issues

🔒

Scope Stability

No mid-sprint surprises or feature injections

🤝

No Hero Culture

Sustainable pace, realistic commitments, team wins

📈

No Blame Culture

Focus on process improvement, not finger-pointing

The Result

This framework creates predictable delivery, high code quality, and sustainable team health. By separating concerns, providing buffers, and enforcing standards, we build software that lasts and teams that thrive.
